# 港口靠泊六方协同与延误影响传播

本模块把标准靠泊事件网关输出绑定到一个可复核的共同时间线，覆盖船公司、船舶代理、码头、引航机构、拖轮机构和港口管理机构。它解决的是“延误发生后，谁受影响、哪些资源冲突、建议如何重排、谁已确认或提出异议”，而不是替代任何一方的生产业务系统。

## 共同时间线合同

输入模式为 `port_call_collaboration_dataset.v1`，至少包含两艘船舶和以下内容：

- 标准靠泊事件证据的摘要，用于防止协同计划脱离原始事件版本；
- 六个固定业务角色的稳定身份、组织、授权状态和来源引用；
- 泊位、引航员、拖轮等单体资源及其责任方；
- 从到港、引航开始、靠泊开始、作业开始、作业完成、靠泊完成到离港的顺序里程碑；
- 实际延误事实、发生时间、原因和来源引用；
- 当前协同修订版本，以及绑定候选重排摘要的六方确认或异议回执。

预计、请求、计划和实际仍由上游标准事件网关区分。本模块只处理已进入协同修订的计划时间线，并把上游事件摘要保存在证据中。本合同借鉴港口靠泊协同中的通用事件和时间戳概念，但不声明取得任何外部标准的符合性认证。

## 延误传播与资源重排

算法按以下顺序工作：

1. 校验六方身份、资源责任、时间区、船舶识别号、事件摘要和当前修订回执。
2. 延误从目标里程碑开始沿同一航次的依赖链传播，保留原计划各里程碑之间的时间间隔。
3. 对传播后的泊位、引航员、拖轮、系泊和航道资源占用窗做容量冲突检查。
4. 出现冲突时，按业务优先级选择较低优先级航次，从冲突里程碑起整体顺延，并增加固定十五分钟衔接缓冲。
5. 重新检查所有资源，分别保存重排前冲突、重排动作和重排后冲突，并计算覆盖候选时间线与全部重排动作的提案摘要。
6. 六方回执必须逐条绑定该提案摘要，旧版本或其他方案的回执会被拒绝。任一参与方提出异议、回执不全，或重排后仍有冲突，当前修订状态保持 `needs_revision`；系统不会把它标记为已接受。

重排结果是候选建议。输入计划、真实预计到港时间、引航申请、拖轮预约和码头生产计划均不在计算过程中被修改。

## 现场证据与准入

输出模式为 `port_call_collaboration_evidence.v1`。现场准入要求同时满足：

- 来源等级为经授权的现场协同导出，并由离线流程显式确认；
- 六方身份均已授权，且每方对当前修订只有一条绑定同一提案摘要的可追溯回执；
- 上游靠泊事件摘要为有效的 SHA-256 摘要；
- 重排后资源冲突数为零，未解决异议数为零，六方确认覆盖率为百分之百；
- 码头运营审核人与港口管理机构审核人相互独立，且均不同于数据所有者；
- 变更工单、数据摘要、证据摘要和统一站点标识完整。

通过以上条件只表示协同证据可进入生产准入链。每一次真实计划变更仍需由责任业务系统和有权人员执行确认；该证据不授予预计到港时间修改权、资源预订权、指令下发权或生产控制权。

## 接口与离线工具

- `GET /api/v3/port-call-collaboration/readiness`：读取已配置的版本化现场证据状态；未配置时失败关闭。
- `POST /api/v3/port-call-collaboration/run`：只计算浏览器或接口提交的候选证据；永不审批、保存或写回生产计划。
- `python -m scripts.verify_port_call_collaboration --input ... --output ...`：生成新的版本化离线证据。输出文件已存在时拒绝覆盖。

生产环境通过 `PORT_DT_PORT_CALL_COLLABORATION_PATH` 指向私有证据。该证据与孪生图谱、现场标定、影子验收和执行联锁证据的 `site_id` 必须一致，否则 `/health/ready` 保持 `production_site_ready: false`。
